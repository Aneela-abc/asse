# System Design Write-up (Streamlit Edition)

## 1. Double-booking prevention
Booking validates the requested time against the doctor's working days, hours, slot duration and leave list. The critical operation then opens a SQLite `BEGIN IMMEDIATE` transaction, which serializes competing writers before the availability check runs. A partial unique index on `(doctor_id, start_at)` applies to active appointment states (`HELD`, `CONFIRMED`, `COMPLETED`). Even if two Streamlit sessions submit a booking for the same slot at nearly the same moment, only one INSERT can commit; the other hits `sqlite3.IntegrityError`, which `core.book_appointment` catches and converts into a friendly `BookingConflict` shown in the UI. This is enforced at the database boundary, not just in the UI, so it holds even under concurrent access from multiple browser tabs/users.

## 2. Doctor leave conflicts
Doctor profiles store leave dates. Slot discovery excludes leave days, and booking re-checks server-side (`core.slot_ok`). When a doctor or admin adds a leave day through the profile form, `core.admin_update_doctor` searches confirmed appointments on that date, cancels them, and writes a durable `LEAVE_CONFLICT` notification for every affected patient — surfaced immediately in the UI ("N appointment(s) cancelled and patients notified").

## 3. Slot hold mechanism
The schema retains `HELD` and `hold_expires_at` columns. The current flow confirms immediately inside the same atomic transaction that checks availability, which is sufficient because the whole booking (validation → conflict check → insert) happens in one `BEGIN IMMEDIATE` block — there is no multi-step client round-trip during which a slot could be "reserved but abandoned." For a payment-gated or multi-step booking flow, the same state model supports a short-lived `HELD` row created first, then converted to `CONFIRMED` on completion, with a scheduled cleanup job releasing expired holds.

## 4. Notification failure handling
Notifications are never sent inline as part of the booking transaction. Booking, cancellation, leave conflicts, and post-visit summaries all insert a `QUEUED` row into `notifications` first. `core.process_notifications` (triggered opportunistically on each Streamlit page load via `run_background_jobs_if_due`, and manually from the Admin → Notification queue tab) attempts delivery, records `attempts`/`last_error`, and schedules `next_attempt_at` with exponential backoff on failure. A temporary SMTP outage therefore never rolls back a valid appointment, and the patient/doctor can always see the notification and its status in the in-app "Notifications" tab even before email delivery succeeds. Without SMTP configured, sends succeed in a documented "demo mode" so the full workflow is inspectable offline.

**Streamlit-specific note on background jobs:** Streamlit has no long-lived daemon process shared cleanly across reruns/sessions, so instead of a `threading` worker loop (as in the original HTTP server), the queue sweep is throttled via a `job_state` table (`run_background_jobs_if_due`) and runs opportunistically whenever any user's page reruns, plus on-demand from the admin panel. This keeps behavior correct under Streamlit's execution model without spawning duplicate worker threads per session.

## 5. LLM reliability
The LLM is an enhancement, not a dependency for booking correctness. Prompts demand structured JSON and explicitly forbid diagnosis or invented medication details. `core.llm` catches network, auth, and parsing errors and returns `None` on any failure; `core.previsit`/`core.postvisit` then fall back to a deterministic, rule-based summary with the same JSON shape, so the UI and database never break even with no API key configured or an outage mid-conversation.

## 6. Database and API design
The schema separates identity (`users`), doctor configuration (`doctors`), transactional care events (`appointments`), asynchronous communication (`notifications`), external calendar sync (`calendar_events`), and scheduled medication reminders (`medication_reminders`). `core.py` exposes a small set of pure functions (`book_appointment`, `cancel_appointment`, `complete_appointment`, `admin_update_doctor`, …) that raise `AppError`/`BookingConflict` on business-rule violations, which the Streamlit layer converts into `st.error`/`st.warning` messages — the same separation of concerns an HTTP API would have between service layer and transport layer, just without the HTTP hop.

## 7. Calendar integration
Every confirmed appointment is always given a downloadable `.ics` calendar file (works with Google Calendar, Outlook, Apple Calendar, etc. with zero configuration). When `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` are set, the app also offers real Google Calendar OAuth 2.0: the "Connect Google Calendar" link sends the user to Google's consent screen with `redirect_uri` pointing back at the deployed Streamlit app URL; Streamlit's `st.query_params` reads the returned `code`/`state` on the next page load and completes the token exchange (`core.google_token_exchange`), after which `core.sync_calendar_booking` creates a real event on booking for any user with a stored token.

## 8. Production hardening
For a real clinic: move from SQLite to PostgreSQL, add a hardened identity provider or session/token rotation instead of plaintext session state, encrypt tokens and PII at rest, add audit trails, HTTPS, rate limiting, secret management, structured logging/monitoring, backups, and a formal privacy/security review. The submission deliberately keeps the runnable core dependency-light (SQLite + stdlib + Streamlit) while preserving clear seams for those production services.
